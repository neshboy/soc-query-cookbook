# Part 28 — Maintaining the Cookbook: Coverage, Freshness & Debt

## Why this part exists

**[CONCEPT]** This part carries no query-pattern budget — the same em dash BOOK-INDEX.md assigns Parts 1 and 2 — and no new `QC-NN-SS` ID originates here. It is a synthesis part, exempt from the pattern skeleton entirely (STYLE-GUIDE.md §11), built from ordinary prose sections rather than a header table, `[HUNTER]`/`[QUERY]`/`[FALSE POSITIVE]`/`[PIVOT]` tags, or a language-coverage row. Nothing below is a hunt starting point; everything below is about what happens to the roughly 140 hunt starting points this book publishes, after publication, once a real team starts copying them into real consoles.

This book's own Part 2 §5 already answered the narrow question of where one freshly copied pattern sits on Detection Engineering Handbook V2's (DEH) six-tier Detection Coverage scale (DEH Part 41), and closed by naming exactly the job this part exists to do: "Aggregating that mapping across the whole catalog — which patterns are still exploratory, which have graduated, where debt is accumulating — is Part 28's job, applying DEH Parts 41–43's methodology to the catalog as a body of work rather than one pattern at a time." This part does not re-derive Part 2 §5's per-pattern ladder, and it does not re-teach DEH Part 41's six tiers, DEH Part 42's quality metrics, or DEH Part 43's five debt types from scratch — BOOK-INDEX.md is explicit that this book does not own coverage, quality, or debt methodology, and a reader who wants those definitions in full goes to DEH directly. What this part adds is the layer DEH never had to build for itself: a way to track a body of published, un-deployed, illustrative query patterns as they get adopted, unevenly, across an unknown number of reader environments this book's authors will never see — without inventing a second scoring system next to DEH's existing one.

The boundary against Part 27 is equally direct: Part 27's hunt chains sequence existing pattern IDs into worked investigative narratives ("run `QC-05-02`, then `QC-15-03`, then `QC-16-01`"). This part never sequences patterns — it tracks the state of each one, one row at a time, independent of any chain it might belong to.

## 1. Why the catalog needs its own ledger, distinct from Appendix A1

**[CONCEPT]** Appendix A1 (Master Pattern Index) and Appendix A2 (Behavior × Language Coverage Matrix) already track every `QC-NN-SS` pattern this book publishes: its title, owning part, MITRE mapping, and which of the six languages are covered versus marked `N/A`. That is a catalog-of-the-book structure, built once by this book's own authors and maintained on this book's own release cadence. It answers "does this pattern exist, and in which languages" — nothing else.

A reader's adoption of any given pattern is a completely separate fact, and this book cannot track it for them. Part 2 §5 states the underlying reason precisely: a tier on DEH's six-tier scale is "always earned by the reader's own evidence, never inherited from the fact that a query appears in a published cookbook." The same logic scales up unchanged from one pattern to the whole catalog — a reader's copy of Appendix A1 tells them what this book offers; it says nothing about what their own team has actually run, tuned, graduated, or let go stale.

Call the artifact this part is actually about a **Pattern Adoption Ledger** — not a new proper noun this book is coining as a fourth methodology, just a descriptive label for "DEH Part 41's coverage-matrix row schema (DEH Part 41 §3.1), populated with cookbook pattern IDs instead of bare technique IDs, and maintained by the adopting team, not by this book's authors." A row needs everything DEH Part 41 §3.1 already requires of a coverage-matrix row — technique ID, tier, telemetry source, owning Detection Rule ID, a dated evidence reference, a last-validated date, an owner, and a named gap for anything below `MULTI-SOURCE DETECTION` — plus exactly one additional column this book's shape makes necessary: the `QC-NN-SS` pattern ID the row's rule was adapted from, so a team can trace a live detection back to the cookbook entry that seeded it. Nothing else about the schema changes.

> **Engineering Reality**
> A team that skips building this ledger and instead just checks off patterns in their own copy of Appendix A1 ("adopted: yes/no") has quietly rebuilt the exact all-green-heatmap problem DEH Part 41 §1.1 opens by naming, one layer removed: a checkmark next to a pattern ID answers "did someone at some point copy this query somewhere," not "does a tuned, owned, currently firing detection exist because of it." Appendix A1's own schema has no tier column and was never meant to carry one — it is this book's index, not any reader's operational record.

## 2. The adoption-status axis is not the same as the tier axis

**[CONCEPT]** Two different questions get asked about any adopted pattern, and conflating them is the single most common mistake a Pattern Adoption Ledger makes on its first draft.

The first question is operational: has this pattern been run at all, and if so, on what basis? DEH's TERMINOLOGY.md draws the exact line this book needs here. A **Hunt** is "a time-boxed, hypothesis-driven, human-led investigation into a behavior with no reliable standing detection (or one that may never get one), conducted to prove or disprove a Threat Hypothesis against real telemetry in the absence of a fired alert... [that] must end in either a documented negative finding ... or a new detection candidate — never in 'nothing found, moving on' with no artifact left behind... [and is d]istinct from a Detection Rule in that it is manual and time-boxed, not automated and continuous." A **Detection Rule** is "the literal, deployed, versioned logic ... that evaluates live telemetry and produces alerts... with its own lifecycle (deployed, tuned, deprecated)." A cookbook pattern copied out of this book and run by hand once is a Hunt. The same pattern, adapted, scheduled, and given disposition history, is a Detection Rule. Nothing in between those two states deserves to be called "coverage" of anything.

The second question is evidentiary, and it is exactly DEH Part 41's six tiers: given that a pattern has been run, or scheduled, how strong is the evidence that it actually works? A pattern can sit at either end of the first axis and still land anywhere on the second. A pattern run once as a hunt, with a documented negative finding, tells a team something real and dated — but it is not evidence toward `PARTIAL DETECTION`, because `PARTIAL DETECTION` requires a deployed analytic with a named gap, not a one-off check. A pattern that has been graduated into an owned, scheduled rule can still sit at `PARTIAL DETECTION` for months if its false-positive rate has never been measured against production disposition data.

The table below names the four adoption states a Pattern Adoption Ledger's rows actually take, and states plainly what tier claim, if any, that state alone supports — deliberately narrower than what most teams assume on a first pass.

*(CONCEPTUAL SAMPLE — a reasoning aid, not a scored claim about any specific pattern or reader environment.)*

| Adoption state | What actually happened | Tier claim this state alone supports |
|---|---|---|
| Cited only | The pattern appears in a team's reading list or internal wiki link; nothing has been run. | None — not even `NO VISIBILITY`, which itself requires a checked, named absence, not silence. |
| Hunted ad hoc | Run once or a handful of times by hand, as a time-boxed Hunt, with a documented finding (positive or negative). | None toward the pattern's own tier — the finding is evidence about the underlying technique's honest state, filed per DEH's TERMINOLOGY.md § Hunt, not evidence that a rule now exists. |
| Graduated, untested | Adapted to the team's schema, deployed as an owned, scheduled Detection Rule, with `[FALSE POSITIVE]` items from the pattern carried into a documented gap; no disposition history collected yet. | `PARTIAL DETECTION` — an analytic exists with a named gap, no more. |
| Graduated, measured | The above, plus disposition history collected over a stated window at an acceptable false-positive rate. | `RELIABLE DETECTION` or higher, per DEH Part 41 §2.1's remaining tiers, depending on source count and testing recency. |

A ledger that only records "adopted: yes" is silently rounding every row in this table up to whatever the reader hopes it means. The whole discipline this part is built around is refusing that rounding.

## 3. Aggregating tier claims across a growing catalog

**[CONCEPT]** DEH Part 41 §4.1 builds a worked, ten-row matrix mixing all six tiers honestly, specifically to demonstrate that a real coverage picture skews heavily toward the lower tiers rather than landing evenly across all six. The same demonstration applies directly to a Pattern Adoption Ledger, and the same honest-skew expectation holds: most patterns a team has touched at all should sit at `PARTIAL DETECTION` or below, with only a handful reaching `MULTI-SOURCE DETECTION` or `TESTED / RECENTLY VALIDATED`, at least in the first year or two of adopting this book's catalog.

The worked snapshot below tracks nine adopted rows out of this book's roughly 140 published patterns — a small, early-stage adoption slice, not a claim about how much of the catalog any real team should have touched by any particular point.

*(CONCEPTUAL SAMPLE — illustrative adoption snapshot, not captured from a live program.)*

| Pattern ID | Mapped technique | Adoption state | Tier | Last validated (this team) |
|---|---|---|---|---|
| `QC-04-02` | T1110.001 (Password Guessing) | Graduated, measured | RELIABLE DETECTION | 2026-08-11 |
| `QC-05-02` | T1110.003 (Password Spraying) | Graduated, untested | PARTIAL DETECTION | — |
| `QC-16-01` | T1543.003 (Windows Service) | Hunted ad hoc | — (finding only) | 2026-07-02 |
| `QC-16-03` | T1047 (Windows Management Instrumentation) | Cited only | — | — |
| `QC-08-01` | T1059.001 (PowerShell) | Graduated, measured | MULTI-SOURCE DETECTION | 2026-09-01 |
| `QC-09-02` | T1218 (System Binary Proxy Execution) | Graduated, untested | PARTIAL DETECTION | — |
| `QC-11-01` | T1136 (Create Account) | Cited only | — | — |
| `QC-14-01` | T1070.001 (Clear Windows Event Logs) | Graduated, measured | RELIABLE DETECTION | 2026-06-19 |

Reading the "Last validated" column against "Adoption state" is the point, exactly as it is in DEH Part 41's own matrix: four of the nine rows carry no validation date at all, because a row that has never been graduated into a scheduled rule has nothing to validate yet. A ledger template that forces a date into those cells anyway is manufacturing the same false confidence DEH Part 41 §4.1 warns a green heatmap cell creates — it should stay blank, or read `— (not yet applicable)`, not get filled in to satisfy a spreadsheet column.

> **Blind Spot**
> A snapshot table like the one above answers "where do things stand today." It cannot answer "how long did `QC-05-02` sit at `PARTIAL DETECTION` before anyone circled back to measure it." DEH Part 41 §2.2's own caution applies without modification: store a dated tier-change history per ledger row, not just a current-state field. A pattern graduated in March and never revisited looks, in a snapshot view, identical to a pattern graduated last week — and only the history distinguishes a team that is actively working its way up the tiers from one that graduated a rule once and walked away.

## 4. Two clocks, not one: reader-side drift and book-side drift

**[CONCEPT]** DEH Part 43 defines five debt types — telemetry, parser, testing, documentation, and tuning debt — each describing a way a *deployed, currently operated* detection silently drifts from what it was built to do. Every one of those five types transfers to a graduated cookbook pattern with no modification at all: a `QC-04-02`-derived rule that stops seeing a source-address field because of an agent migration has exactly DEH Part 43 §2.2's parser debt, whether the rule's logic originated in this book or was authored from scratch. Nothing about a rule's cookbook ancestry changes how it decays once it is running.

But a rule that is running is not the only artifact this book has to worry about staying honest. This book itself is a static, versioned text file describing query syntax against six vendor surfaces this book's authors do not operate, cannot canary-test, and do not control the release schedule of. That is a second, genuinely distinct clock, and it ticks whether or not any reader has adopted the pattern at all.

### 4.1 The reader-side clock

A pattern graduated into a reader's own environment accrues DEH Part 43's five debt types exactly as any other rule does. Nothing in this section changes that; the ledger built in §§1–3 above is the correct place to track it, using the same evidence, the same recency windows, and the same blast-radius-versus-remediation-cost prioritization DEH Part 43 §4 already defines. A team should not build a second debt-tracking process for cookbook-derived rules specifically — a `QC`-prefixed pattern ID in the ledger's "originating pattern" column is the only thing distinguishing these rows from any other entry in the same team's broader detection-debt ledger, and that column exists purely for traceability, not because the debt itself behaves differently.

### 4.2 The book-side clock

The second clock has no DEH precedent, because DEH's own queries are DEH's real, reviewed, currently operated detections (STYLE-GUIDE.md §12) — if DEH Part 24's Sigma rule for `lsass.exe` access goes stale against a schema change, DEH's own production monitoring (a rule-failure canary, DEH Part 42 §10) catches it the moment it stops firing, because someone is running it continuously. This book's queries sit dormant in a published page until a reader copies one, sometimes years after the page was written, against a vendor surface that has kept evolving the whole time this book has not. A Sentinel table gets renamed or deprecated. A Sigma taxonomy version bump changes a `logsource` mapping. A QRadar release changes which AQL aggregate functions a `HAVING` clause accepts. None of that produces an error in this book — a static Markdown file cannot fail a query — so the staleness sits invisibly correct-looking on the page until the exact moment a reader pastes it into a console expecting it to run, which is a worse discovery moment than a live pipeline's silent zero-alert failure: a running rule's own disposition history at least gives an analyst a baseline to notice against, where a reader trying a cookbook query for the first time has no baseline at all and may simply assume the empty result means "no matches" rather than "wrong table name."

This is not a sixth debt type. It maps cleanly onto two of DEH's existing five: it is parser debt scoped to this book's own assumed schema rather than any single reader's ingest pipeline, and it is testing debt in the specific sense that nothing re-validates a published pattern's syntax against current vendor documentation on any schedule at all unless a curator deliberately does so. Naming it as a variant of two categories DEH Part 43 already defines — rather than inventing a parallel "cookbook freshness score" — is the concrete answer to BOOK-INDEX.md's own instruction that this part apply existing methodology, not build a new one.

The fix is mechanical, not novel: extend Appendix A1 and A2 — which already track, per pattern, which languages are covered versus `N/A` — with one additional field per language block: a last-checked-against-vendor-docs date, maintained by whoever curates future editions of this book, exactly mirroring the mandatory `last_validated` field BOOK-INDEX.md's production model already requires of every chapter file. The only difference is granularity: a chapter's front-matter `last_validated` date is one value for the whole file, but one part can hold five or six patterns across up to six languages each, and a single vendor's schema change affects one language block in one pattern, not the whole part. Appendix A1 is the right place to track that granularity because it already exists as a per-pattern index; inventing a second index for freshness alone would be exactly the parallel scoring system this part is instructed to avoid.

> **Engineering Reality**
> Nothing about DEH's own detection-debt tooling catches book-side staleness automatically, and nothing should be expected to — a rule-failure canary (DEH Part 42 §10) only works because something is running continuously against live telemetry, and a published book page is not running anything. Closing this gap is a manual curation task: periodically re-reading a sample of published patterns against current vendor documentation, the same unglamorous, non-automatable work DEH Part 43 §1's own Engineering Reality box names for a detection-debt ledger in general, just aimed at this book's own catalog instead of a SOC's deployed rule set.

## 5. Worked example: one pattern, both clocks, one ledger

**[CONCEPT]** `QC-04-02` (High-volume failed SSH authentication against a single account, T1110.001) is a useful pattern to walk through in full, because DEH Part 43 §3 already built a complete five-row debt ledger for the identical underlying analytic under its own ID, `DET-43-01` — same source telemetry (`btmp`-derived failed-SSH events), same threshold shape (ten or more failed attempts against one account inside a five-minute window), same real captured evidence (`ct104-vulnscan-ssh-failed-logins-btmp.txt`). A team that graduates `QC-04-02` verbatim is not starting a debt ledger from a blank page; they are inheriting DEH Part 43 §3's ledger for free, and the only genuinely new work is adding the row DEH Part 43 had no reason to include, because DEH was never worried about its own queries going stale on the page.

*(CONCEPTUAL SAMPLE — illustrative ledger entry combining DEH Part 43 §3's worked reasoning with this book's own freshness column; not captured from a live program.)*

| Debt type | Status for a `QC-04-02`-derived rule | Owed fix |
|---|---|---|
| Telemetry debt | Open — no visibility into pre-authentication protocol-negotiation failures, per DEH Part 43 §2.1's own finding for this exact analytic | Onboard `sshd` pre-auth failure telemetry as its own source with its own analytic |
| Parser debt (reader-side) | Not currently open — the rule's three depended-on fields (source, account, action) are simple and unobserved to mis-parse | Re-check after any authentication-log parser or agent version change |
| Parser debt (book-side) | Open by default until checked — the KQL block targets Sentinel's `Syslog` table; if that table's schema or connector changes, this pattern's KQL block goes stale independent of anything in any reader's own environment | Curator re-validates the KQL block's table and field names against current Sentinel documentation on a fixed cadence, records the date in Appendix A1 |
| Testing debt | Open — no adversary-emulation record ties this rule to a re-test after any recent host or agent change | Schedule a recurring atomic test tied to environment-change events |
| Documentation debt | Open — no recorded rationale for the ten-in-five-minutes threshold beyond "this book's illustrative default" | Write the threshold's origin and any local tuning history into the rule's own record |
| Tuning debt | Open — a recurring, correctly-matched internal misconfiguration (the same device DEH Part 43 §3 identifies) has no on-file exception yet | Add a named, dated Exception scoped to the specific device, never a blanket internal-source allowlist |

Five of the six rows are DEH Part 43's own reasoning, cited rather than re-derived. Exactly one row — book-side parser debt — is this part's own contribution, and it is the row a team adopting any cookbook pattern should add to every ledger entry that cites a `QC-NN-SS` ID, regardless of which behavior the pattern covers.

## 6. Quality metrics on a graduated pattern: no special-case math

**[CONCEPT]** Once a cookbook pattern graduates into an owned, scheduled Detection Rule, DEH Part 42's quality vocabulary — precision, recall, alert-to-incident ratio, handling time, testing age, suppression tracking, detection drift — applies exactly as written, with zero adaptation for the rule's cookbook origin. A graduated rule is a rule; nothing about where its logic was first drafted changes the arithmetic behind `TP / (TP + FP)`. Restating any of DEH Part 42's formulas here, with a cookbook-flavored label, would be precisely the parallel scoring system this part is instructed not to build.

One genuinely pattern-specific caution is worth naming, though, because it follows directly from this book's own honesty standard rather than from DEH's. STYLE-GUIDE.md §12 requires every query in this book to be labeled `CONCEPTUAL SAMPLE` by default, which means every cookbook-derived rule starts its life with precisely zero disposition history anywhere — not reduced history, none. DEH Part 42 §3 already names the general version of this problem: "a rule that fires once a year, correctly, on a real attack has 100% precision and tells you nothing about the seventeen other real attacks of the same type it silently missed." A freshly graduated cookbook rule is the sharper edge case of that same caution — a precision or recall figure computed from a sample of two or three closed alerts in the first week after graduation is not a thin estimate, it is noise dressed as a metric. Treat DEH Part 42 §3's own illustrative sample — 40 closed alerts over a rolling 30-day window — as a reasonable floor before reporting a precision figure on any newly graduated cookbook pattern, and hold the row at `PARTIAL DETECTION` on the ledger until that floor is met, rather than promoting it to `RELIABLE DETECTION` on the strength of a handful of early, unrepresentative closes.

## 7. Prioritizing paydown across a growing catalog

**[SOC MANAGEMENT]** A team adopting patterns steadily across several parts of this book will accumulate open ledger rows faster than any small team can close them, for the same structural reason DEH Part 43 §4 names for detection debt generally: paying down an existing row produces no new coverage anyone can point to, so it competes poorly against the visible win of graduating one more pattern. Nothing about this part changes DEH Part 43 §4's prioritization axes — blast radius against remediation cost — and nothing here should replace them with a cookbook-specific weighting scheme.

What does change, purely as a matter of scale, is the unit worth reporting. A team tracking nine adopted patterns can review every open row by eye each month. A team that has adopted sixty or more patterns across a dozen parts cannot, and reporting "sixty patterns adopted" invites the identical single-number failure DEH Part 41 §1.2 names for a bare coverage percentage. Roll the ledger up by MITRE tactic or by owning part instead — "of our twelve adopted credential-access patterns, nine are `RELIABLE DETECTION` or higher, two are `PARTIAL DETECTION` with an open telemetry gap, and one has gone six months past its last-validated date with no re-test" is a management-usable sentence with a specific next action attached. "Sixty patterns adopted" is not, and a rollup that only ever grows quarter over quarter is the same all-green heatmap wearing a cookbook's clothing.

## 8. Reporting cookbook adoption upward

> **SOC Management View**
> Never report "we've adopted N patterns from the Cookbook" to a CISO or a board as if it were a coverage statement — it answers a procurement or reading-list question, not a security one, and it invites exactly the follow-up DEH Part 41 §7 warns a single number always invites: "why isn't it higher." The correct shape names the tier distribution across the adopted subset only, which specific rows regressed or went stale against either clock in §4, and which `NO VISIBILITY`/exploratory-only rows are the next graduation candidates. "We graduated four Section D patterns to `RELIABLE DETECTION` this quarter, and one Section C pattern regressed to `PARTIAL DETECTION` after an IdP schema change we're still chasing" is reportable. "Cookbook adoption is up 15% this quarter" is not — it has no attached failure mode, and per DEH Part 41 §7's own standard, a number that only ever goes up in a report deserves the same skepticism as a coverage percentage that never falls.

The same discipline applies one level down, to the six-language format itself. A team should resist reporting "we have six-language coverage for this behavior" the moment a pattern's header table lists all six languages as covered — the header table states what this book publishes, not what the team has adapted, deployed, or validated in any of those six syntaxes. `MULTI-SOURCE DETECTION` (DEH Part 41 §2.1) requires two independently validated sources, not two syntax blocks sitting next to each other on a page; Part 2 §5 makes exactly this point for a single pattern, and it holds without modification when a team reports across its whole adopted set.

## 9. Where the dual-clock model earns its complexity, and where it doesn't

> **What Would Change My Mind**
> This part treats the book-side freshness clock (§4.2) as worth tracking separately from ordinary reader-side detection debt, on the theory that a static reference catalog spanning six independently evolving vendor surfaces accrues staleness in a way a single team's own operated rule set does not. If a curator maintaining this book's Appendix A1 found, in practice, that book-side syntax drift was rare enough — because the six vendor surfaces' query syntax for the behaviors this book covers changes far less often than their UI or their marketing does — that the added ledger column in §4.2 mostly sat empty and unused across several real editions, that would be evidence the two-clock framing is more caution than this book's actual maintenance burden justifies, and a future edition should fold the book-side check into an ordinary pre-release review pass rather than a standing per-pattern-per-language field.

For a small team adopting a handful of patterns, the full machinery in §§1–6 above — a dedicated ledger, a tracked tier-change history, a rollup by tactic — is more process than nine rows justify; a shared spreadsheet with the columns named in §1 and a monthly five-minute review is enough. The point of naming the full model is not that every team needs every piece of it immediately. It is that when a team's adopted set grows past what one person can hold in their head — and every team that keeps graduating patterns eventually crosses that line — the schema to grow into already exists, borrowed whole from DEH Parts 41–43, and nobody has to design it under deadline pressure after the first incident that exposes a stale row nobody was tracking.

## Summary

Three things distinguish a healthy adoption of this book's catalog from an unhealthy one, and none of them require any methodology this book invented for itself. First, a Pattern Adoption Ledger, keyed by `QC-NN-SS` ID, is a distinct artifact from Appendix A1 — the book's index describes what exists to be adopted; the ledger describes what actually has been, using DEH Part 41's own coverage-matrix schema with one traceability column added. Second, "exploratory-only" and "graduated" are operational states, not evidentiary tiers, and a ledger that collapses the two into a single checkmark is rounding every row up to whatever the reader hopes it means. Third, a cookbook pattern accrues debt on two clocks, not one — DEH Part 43's five familiar types once it is deployed in a reader's own environment, plus a book-side variant of parser and testing debt that ticks whether or not anyone has adopted the pattern at all, closed the same unglamorous way DEH Part 43 closes every other kind of debt: a maintained, dated, honestly reviewed row, not a dashboard that assumes silence means health.
